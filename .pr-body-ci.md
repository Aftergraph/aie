## What

GitHub Actions on the `JonasAbde` account is billing-locked, which blocks the GH-hosted `ci.yml` matrix and the `aie-v04-s1-self-hosted.yml` artifact upload. PR #25 (`fix/sep-2575-sse-stream-passthrough`) cannot run CI for the same reason.

Add an in-house CI workflow on the existing VDS self-hosted runner (the same `aie-interop` box that already runs the S1.1 external interop gate). The workflow job's own result already becomes a commit-status check on the PR, so no separate status publisher is needed in the workflow itself.

## Layout

- **`.github/workflows/aie-v04-ci-self-hosted.yml`**: 3-Python (3.11/3.12/3.13) matrix, `runs-on: [self-hosted, linux, x64, aie-interop]`. Triggers on `pull_request` + `push:main`. Installs `uv` (single static binary, no sudo) and the matrix Pythons on demand. Creates a per-job venv at `RUNNER_TEMP/venv-<py>` and prepends it to `GITHUB_PATH` so bare `python` resolves to the matrix interpreter. Runs `pip install -e .[dev,otel]`, `compileall -q src interop/s1`, `pytest -q --junitxml=...`. Persists runner-local evidence to `/home/aie-runner/aie-ci-results/<run_id>-<run_attempt>/`.
- **`tools/ci_status_publisher.py`**: ~85-line stdlib-only script that posts a commit status via `gh api repos/<repo>/statuses/<sha>`. Kept as a standalone tool for ad-hoc/manual status posts from outside a GH Actions run (Jonas's Windows box, a manual canary from the VDS, future webhooks). Not invoked from the workflow itself.
- **`tests/test_ci_status_publisher.py`**: 8 unit tests lock the publisher's contract.
- **`docs/inhouse-ci-research.md`**: 5-page research report with the option matrix, failure modes, and validation plan.

## Why this design

- No second self-hosted runner, no Drone/Buildkite. The S1.1 gate is infrequent (`workflow_dispatch`) and contention is theoretical.
- GH-hosted `ci.yml` stays as a redundant fallback. Branch protection rule is unchanged — it just sees the same context from a different publisher.
- Python publisher, not bash, because argv quoting for `gh api` (parentheses in context names, long descriptions) is fragile in bash.
- The first in-house run (33818434993) failed with rc 127 on every step that called `python` because the bare `python` wasn't on PATH. Fixed by creating a venv and adding it to GITHUB_PATH. The follow-up run (33818555405) passed all 3 jobs (3.11/3.12/3.13) in ~64s each.

## Why a separate publisher exists at all

The publisher isn't called from the workflow — the job result is already a commit status. It's there for **out-of-band** scenarios:

- A future local CI script (Jonas's Windows box) that wants to post a status.
- An ad-hoc canary run from the VDS that bypasses GH Actions entirely.
- A webhook from another system that wants to light up a `ci/...` context.

The 8 unit tests lock its contract so it can be invoked safely from any of these.

## Failure modes

- Runner offline → GH Actions still works, the fallback `ci.yml` runs when billing is healthy.
- Runner online, billing locked → in-house path posts statuses; PR check is green if tests pass; merge proceeds.
- Both down → admin-override, recorded in CHANGELOG.
